# 变更提案: 后端完整商城 MVP

## 需求背景
当前项目已经具备高并发秒杀的库存扣减、异步订单、Outbox、死信补偿和可观测链路，但业务在“订单异步创建成功”处结束。项目缺少真实用户、商品目录、购物车、结算、支付、履约、售后和标准化工程交付能力，无法形成完整商城后端闭环。

本次暂缓所有商城前端工作，只实施后端 API、领域模型、数据迁移、部署与自动化验收。

## 产品分析

### 目标用户与场景
- **消费者:** 注册登录、维护地址、浏览 SKU、加入购物车、下普通或秒杀订单、支付并查看履约状态。
- **运营人员:** 通过受保护 API 管理商品、库存、秒杀活动、发货和退款。
- **开发维护者:** 一键启动依赖和服务，通过测试及可观测性验证关键交易链路。

### 价值主张与成功指标
- **价值主张:** 保留现有秒杀工程能力，同时形成可演示、可测试、可继续演进的完整后端交易闭环。
- **成功指标:** 核心 API 有自动化验收；金额无浮点计算；订单状态转换受约束；重复请求、支付回调和消息消费保持幂等；`go test ./...` 与 `go vet ./...` 通过。

### 人文关怀
用户凭证使用强哈希，日志不记录密码和 Token；地址等个人信息仅在授权范围内返回；支付使用 Mock/沙箱，不采集银行卡等真实支付敏感数据。

## 变更内容
1. 建立可迁移的 `cmd/`、`internal/` 领域结构和显式依赖注入基础。
2. 新增用户认证、刷新令牌、地址和基础 RBAC。
3. 扩展商品为分类、SPU、SKU、图片、上下架、库存预占和秒杀活动模型。
4. 新增购物车、价格快照、结算、统一订单状态机和幂等创建。
5. 新增 Mock 支付、超时关单、发货、确认收货、取消和退款流程。
6. 将秒杀订单接入统一订单状态及库存预占/确认/释放语义。
7. 增加版本化 HTTP API、数据库迁移、业务服务容器化、测试和验收脚本。

## 影响范围
- **模块:** Gateway、Identity、Catalog、Inventory、Cart、Order、Payment、Fulfillment、Messaging、Platform。
- **文件:** 现有 Go 服务、Proto、SQL、Compose、README、`helloagents/` 知识库，以及新增 `cmd/`、`internal/`、`migrations/`、`tests/`。
- **API:** 新增 `/api/v1` 用户、地址、商品、购物车、订单、支付与运营接口；保留现有秒杀接口的兼容期。
- **数据:** 新增身份、目录、交易、支付、履约、Inbox 和库存预占表；现有金额和订单状态需要迁移。

## 核心场景

### 需求: 用户身份与地址
**模块:** Identity

#### 场景: 用户注册并登录
- 密码使用 bcrypt 哈希，重复账号被拒绝。
- 登录返回短期访问令牌和可轮换的刷新令牌。
- 用户只能维护和读取自己的地址。

### 需求: 商品目录与购物车
**模块:** Catalog、Cart

#### 场景: 用户选择在售 SKU
- 列表与详情只返回已上架商品和 SKU。
- 购物车保存 SKU、数量，并在结算时重新校验价格和库存。

### 需求: 普通订单闭环
**模块:** Order、Inventory、Payment、Fulfillment

#### 场景: 用户从购物车结算
- 使用幂等键创建包含商品与地址快照的待支付订单。
- 库存先预占，订单创建失败或超时关闭时释放。
- Mock 支付成功后订单进入已支付，库存转为已售。
- 运营人员发货，用户确认收货后订单完成。

### 需求: 取消与退款
**模块:** Order、Payment、Inventory

#### 场景: 用户取消或申请退款
- 待支付订单可取消并释放库存。
- 已支付未发货订单可发起 Mock 退款，退款回调幂等更新订单并恢复库存。
- 非法状态转换被拒绝并记录审计信息。

### 需求: 秒杀统一交易
**模块:** Inventory、Order、Messaging

#### 场景: 秒杀资格通过后创建订单
- Redis Lua 只负责准入和库存预占，不再等同于订单最终成功。
- 秒杀订单进入与普通订单一致的待支付、支付、关闭和履约状态。
- 重复消息通过 Inbox 或业务唯一键幂等处理。

### 需求: 后端可部署与验收
**模块:** Platform

#### 场景: 本地启动并运行验收
- 数据迁移可重复执行，所有业务服务具备健康检查和优雅停机。
- 自动化测试覆盖主流程、异常状态、幂等和权限边界。

## 风险评估
- **风险:** 一次性重写现有秒杀链路容易引入库存与补偿回归。
- **缓解:** 采用兼容迁移，先引入新模型和适配层，再切换消费者，旧接口保留至验收完成。
- **风险:** 支付与个人信息属于高风险边界。
- **缓解:** 本轮仅实现 Mock 支付，不保存真实支付凭证；地址 API 强制资源归属校验并避免敏感日志。
- **风险:** 服务继续共享表会固化错误边界。
- **缓解:** 即使本地共用一个 MySQL 实例，也按领域划分表所有权，禁止跨领域直接写表。
